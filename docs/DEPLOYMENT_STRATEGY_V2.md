## 一、核心架構決定 (為什麼這樣選)

### 採用「雙平台 + 共享 DB」

| 用戶 | 訪問 | 平台 | 預期延遲 |
|---|---|---|---|
| 🇭🇰 香港 (你) | Vercel hkg1 | Vercel | API 5-50ms |
| 🇨🇦 加拿大 (合夥人) | Vercel hkg1 | Vercel | API 150-200ms |
| 🇨🇳 中國 | DNS 自動分流 | 阿里雲 FC | API 30-50ms |
| 🇦🇺 澳洲 (未來) | Vercel hkg1 | Vercel | API 120-150ms |

**為什麼不只一個平台**：
- 單 Vercel → 中國用戶打不開（GFW）
- 單阿里雲 → 加拿大合夥人 200ms+，犧牲核心用戶
- 雙平台 → 各取所長，但維護成本+1

### 為什麼不先試單平台再升級

- 「先試再升」聽起來簡單，但**每次升降都要碰 DNS、用戶、key**
- 真實體驗資料可能不準（樣本太少就下結論）
- 維護兩套部署的「心理負擔」可能比「多 200ms 延遲」還累

**反對這個決定的聲音 (我幫你列出來)**：
- 「多花一份維護成本」→ 但都是 code 一份，部署兩處，**其實只是 s.yaml 多幾行**
- 「DNS 切換複雜」→ 阿里雲 DNS 是圖形介面，**5 分鐘設定好**
- 「加拿大合夥人真的會抱怨嗎？」→ 不知道，**這是假設要驗證的**

## 二、Git 分支策略 (防止「一 push 就壞」)

```
dev branch (我開發用)
    ↓
PR 開出來
    ↓
GitHub Actions 自動建 preview URL
    ↓
你/合夥人點開看 → 確認 OK
    ↓
merge 到 main
    ↓
你「手動」按 GitHub Actions 部署按鈕
    ↓
production 上線
```

**為什麼要這樣**：
- 自動 push = 自動部署 = 容易爆
- 手動批准 = 你永遠是最後一道關卡
- Preview URL = 壞了不影響用戶

**可能漏的問題**：
- ❓ Preview 環境要不要連真的 DB？ (預設: 不連，用 mock)
- ❓ Preview 的 URL 怎麼分享給合夥人看？ (預設: 我截圖)
- ❓ dev 和 main 長期分叉怎麼辦？ (預設: 一週 merge 一次)

## 三、Key 管理策略 (零常駐密鑰的偽命題)

> **重要承認**: 我原本說的「零常駐密鑰」其實是**不切實際的**。
> 真正能做的只是「**降低暴露 + 限制權限**」。

### 折衷方案

| | 方案 A: 凍住 (每次啟用) | 方案 B: 常駐 + 最小權限 |
|---|---|---|
| 便利 | ❌ 每次要啟用 | ✅ 不用管 |
| 安全 | ✅ 凍住 | ⚠️ 但權限極小 |
| 失敗時最慘狀況 | 沒什麼 | 攻擊者只能重新部署 |

**推薦方案 B**：
- Sub-account **常駐啟用**（你不用每次切）
- IAM 策略**只允許**：
  - 部署到指定 FC 函數
  - 上傳到指定 OSS bucket
  - 查特定 RDS 資料庫
- **不允許**：
  - 開新資源
  - 刪資源
  - 跨帳號操作
  - 高額消費操作

**失敗模式**:
- ❓ Key 被偷 → 攻擊者能做什麼？ → **只能重新部署現有版本**，不能搞破壞
- ❓ Key 過期怎麼辦？ → **GitHub Secrets 換新值**，但要進後台手動
- ❓ 多人協作怎麼管？ → **目前只有你 + 我，不適用**

## 三.五、Region × Endpoint × Key 三者必須配套 (2026-07-31 教訓)

> ⚠️ 這條規矩**是我們付出慘痛代價學到的**——7/31 下午，聊天功能掛了 1.5 小時。

### 故事

7/26 我們把 `DASHSCOPE_BASE_URL` 設成：

```
https://ws-44r167tof2200yam.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
```

這是阿里雲**中國版北京區域**的 maas 端點，配的是中國版控制台（`dashscope.console.aliyun.com`）生成的 key。

當時看起來一切正常，直到 7/31 把 Vercel 機房搬到香港 hkg1：

- hkg1 連不上 `cn-beijing.maas.aliyuncs.com`（跨 GFW）
- 錯誤訊息顯示「網路不順」——**誤導性極強**，其實是 region/endpoint 對不上
- Food Summary 沒事——它不打 AI，只讀本地知識庫
- 聊天整個掛掉

### 規則（永遠記住）

**Key、Endpoint、Region 三者必須配套。換一個就要換全部。**

| 控制台 | 端點 URL | 配的 Key |
|--------|----------|----------|
| 中國版 `dashscope.console.aliyun.com` | `https://dashscope.aliyuncs.com/compatible-mode/v1` 或 `https://*.cn-beijing.maas.aliyuncs.com/compatible-mode/v1` | 中國版 key（在中國控制台生成） |
| 國際版 `modelstudio.console.alibabacloud.com` | `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` | 國際版 key（在國際控制台生成） |

### 部署位置 → 推薦配套

| Vercel 機房 | 用戶群 | 推薦配套 |
|------------|--------|----------|
| `hkg1` (香港) | HK + 東南亞 | 國際版 + 新加坡 region key，端點 `dashscope-intl` |
| `sin1` (新加坡) | 東南亞 | 國際版 + 新加坡 key，端點 `dashscope-intl` |
| 美西 `iad1` | 北美 | 國際版 + 美國 region key |
| `cn-` 開頭 | 中國大陸 | 中國版 + 北京 key，端點 `dashscope.aliyuncs.com` |

### 自我檢查清單（換任何一個之前先問這 3 題）

1. **這個 key 是在哪個 console 生成的？**（中國版 / 國際版）
2. **我要連的端點 URL 屬於哪個體系？**（看 hostname 段）
3. **部署在哪個機房？**（Vercel hkg1 連得到嗎？）

三個答案**必須一致**才動。

### 失敗模式（這個坑真實發生過）

- ❌ **換端點 URL 沒換 key** → 401 invalid_api_key
- ❌ **換 key 沒換端點** → Connection error（從遠端機房連不上）
- ❌ **換 region 沒確認配額** → 之前的「免費用完即停」保護可能不跟著搬

### 教訓（寫進 Mavis SOP）

> **任何 key 換環境前，先確認 key 跟端點的 region 是同一個。**

## 四、Database 策略 (共享 Neon)

### 為什麼用 Neon Singapore

- HK 訪問 Neon Singapore: 30-50ms
- 阿里雲 FC 訪問 Neon Singapore: 30-50ms (走阿里雲骨幹)
- 加拿大訪問 Neon Singapore: 200-250ms (跨太平洋)

**所有平台都連同一個 Neon Singapore DB**。

### 失敗模式 (這個區塊我特別擔心)

- ❓ Neon 掛了怎麼辦？ → **整個站掛了，沒有 failover**
- ❓ 跨太平洋查詢慢怎麼辦？ → **加拿大用戶會抱怨**
- ❓ DB schema 改動怎麼辦？ → **目前沒有 migration 流程，可能鎖表**
- ❓ 資料備份嗎？ → **Neon 預設每天備份，但沒驗證過還原**
- ❓ 用戶個資 (對話內容) 怎麼保護？ → **目前沒加密，靠 DB 密碼保護**

## 五、Rollback 策略 (出包時的救命繩)

### Vercel
- 每個 deployment 保留
- 一鍵「Promote to Production」切回上一版
- **30 秒搞定**

### 阿里雲 FC
- 每個版本保留
- Console 一鍵切換流量
- **30 秒搞定**

### DB schema 改動的 rollback
- ⚠️ **目前沒有方案**
- 如果我加了新欄位，rollback 時**老 code 不認新欄位可能 crash**
- 建議: **DB schema 改動需要 staging 環境先測**
- 短期: **能不改 schema 就不改**

### 失敗模式
- ❓ 怎麼知道要 rollback？ → **需要監控錯誤率**
- ❓ rollback 期間用戶看到什麼？ → **5-15 分鐘的混亂**
- ❓ 我怎麼知道是「程式碼」還是「DB」問題？ → **手動診斷，沒有自動**

## 六、監控策略 (你才知道站活著)

### 最低限度

- ✅ 阿里雲函數計算內建錯誤率
  - 設定「錯誤率 > 5% 通知你 (Email/SMS)」
- ✅ Vercel 內建監控
  - 看 Deployments 頁面就知道有沒有 5xx
- ✅ Neon 連線監控
  - 看 Operations Log

### 失敗模式
- ❓ 你不會每天看監控吧？ → **真的，所以要主動通知**
- ❓ 半夜 3 點掛了怎麼辦？ → **通知到你手機**
- ❓ 怎麼算「掛了」？ → **錯誤率 > 5% 持續 5 分鐘**

## 七、PWA 更新策略 (用戶手機要拿到新版)

### 現狀
- 用戶手機的 PWA **可能永遠停在舊版**
- 因為 service worker 有快取

### 建議方案
- Service worker 偵測新版本
- 自動彈出「Yoai 有新版本，點擊更新」
- 用戶點擊 → 自動重新整理 → 新版生效

### 失敗模式
- ❓ 用戶忽略更新提示怎麼辦？ → **下次進站還會提示**
- ❓ 強制更新會不會嚇到用戶？ → **先做「軟提示」，觀察 1 個月**

## 八、3 個月後可能後悔的事

> **這是我必須承認的「未爆彈」清單**

### 短期 (1-3 個月內會後悔)

- ❓ **30 calls/天/人** rate limit: 太少？太多？
  - 你/合夥人/家人可能打到上限 → 抱怨
  - 也可能根本用不到 30 次 → 浪費
  - **沒資料，要等真實使用才知道**
- ❓ **Single region DB**: 加拿大用戶查詢慢
  - 200ms 對 chat 不重要，但對「載入列表」可能不順
- ❓ **沒有 Analytics**: 不知道用戶用什麼功能
  - 1 個月後完全不知道「哪些功能被用、哪些沒人用」
- ❓ **沒有 Email 通知**: 用戶不會知道有新功能
  - 只能靠他們自己回來看

### 中期 (3-12 個月)

- ❓ **沒有自訂網域**: `*.vercel.app` 給人感覺不專業
  - 買 `yoai.app` 之類的網域
- ❓ **沒有 Landing Page**: 朋友邀請連結進來直接是登入頁
  - 需要一個 marketing 頁面講「這是什麼」
- ❓ **沒有 i18n**: 普通話 + 繁體中文混用
  - 海外用戶 (英文) 可能不適應
- ❓ **沒有 Backup 用戶資料導出**
  - GDPR / 隱私合規問題

### 長期 (1 年+)

- ❓ **PWA 不夠「原生」**: iOS 用戶想用 Widget、Spotlight
  - 可能需要包成 Capacitor / React Native
- ❓ **沒有多語言 AI**: 模型用 Qwen Plus
  - 英文用戶可能效果差
  - 切換到 GPT/Claude 可能更好
- ❓ **商業模式**: 怎麼賺錢？
  - Premium 功能？訂閱？一次性買斷？
  - 不能永遠用你個人 ¥150/月扛
